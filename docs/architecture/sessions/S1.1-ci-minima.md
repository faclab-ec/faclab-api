# S1.1 — CI mínima en los cuatro repositorios

> **Estado:** terminada (2026-10-14) · rama `build/s1-1-ci-minima` · PR faclab-api#111, faclab-invoicing#43, faclab-web#106, faclab-infra#2 · **Etapa 1 — Fundamentos** · **Tamaño:** M · **Repos:** faclab-core, faclab-invoicing, faclab-web, faclab-infra · **Brechas:** G-53, G-56, G-60, G-78

## 1. Identificador y título

`S1.1` — CI mínima en los cuatro repositorios

## 2. Objetivo verificable

Cada PR a `master` en faclab-core, faclab-invoicing, faclab-web y faclab-infra ejecuta en GitHub Actions las mismas validaciones que hoy se corren a mano, y un PR con una prueba rota queda en rojo.

## 3. Problema que resuelve

Ningún repositorio tiene CI. Las regresiones solo se detectan si alguien recuerda correr las pruebas, y el cambio multiempresa de la Etapa 2 tocará las 34 tablas del core.

## 4. Evidencia de la brecha actual

- Solo existe `.github/pull_request_template.md` en core y web; no hay `.github/workflows` en ningún repo (G-53).
- faclab-invoicing ignora `package-lock.json` (`.gitignore:4`) y declara la dependencia `pettier` (`package.json:68`), un paquete que altera el formato al azar (G-56).
- El `.venv` del core usa Python 3.11 y la imagen Docker 3.12 (G-60).
- La cobertura del core se desconoce: el último `.coverage` es de abril 2026 (G-78).

## 5. Componentes y archivos que probablemente se modificarán

- faclab-core: `.github/workflows/ci.yml` (ruff, ty, pytest con cobertura, job con servicio PostgreSQL para `tests/integration/postgres`).
- faclab-invoicing: `.github/workflows/ci.yml`, `.gitignore` (dejar de ignorar `package-lock.json` y `.github`), `package.json` (quitar `pettier`, agregar `prettier` si falta), `package-lock.json`.
- faclab-web: `.github/workflows/ci.yml` (tsc, eslint, vitest, build; Playwright opcional en un job separado).
- faclab-infra: `.github/workflows/ci.yml` (`docker compose config`, shellcheck de `scripts/`).

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- faclab-core: `Makefile`, `pyproject.toml`, `requirements*.txt`, `tests/conftest.py` (cómo se activan las pruebas de PostgreSQL con `TEST_DATABASE_URL`), `alembic/env.py`.
- faclab-invoicing: `package.json`, `.gitignore` (la regla `.*` oculta `.github`), `tsconfig.json`, `vitest.config.mts`, `eslint.config.mjs`.
- faclab-web: `package.json` (CRLF: editar respetando los finales de línea), `vite.config.mts`, `playwright.config.ts`.
- faclab-infra: `docker-compose.yml`, `scripts/*.sh`.

## 8. Tareas concretas en orden

1. Revisar en cada repo cómo se ejecutan hoy lint, tipos, pruebas y build, y qué versión de Python o Node usan.
2. Core: crear el workflow con Python 3.12, caché de pip, `ruff check`, `ruff format --check`, `ty check`, `pytest --cov=src` y un job con servicio `postgres:17` que corra `tests/integration/postgres` con `TEST_DATABASE_URL`. Publicar el reporte de cobertura como artefacto.
3. Invoicing: versionar `package-lock.json` (generarlo con `npm install` y revisar el diff), reemplazar `pettier` por `prettier`, ajustar `.gitignore` para no ocultar `.github`; workflow con Node LTS fijado, `npm ci`, `lint`, `format:check`, `typecheck`, `test`, `build`.
4. Web: workflow con `npm ci`, `tsc --noEmit`, `lint`, `test`, `build`. Playwright en un job separado y no bloqueante hasta que sea estable.
5. Infra: workflow que valide `docker compose config -q` con `.env.example` y corra shellcheck sobre los scripts.
6. Fijar las versiones de las acciones de GitHub por versión mayor o SHA.
7. Documentar en el README de cada repo cómo correr localmente lo mismo que corre CI.
8. Con mi confirmación, hacer push de las ramas y abrir un PR de prueba con una falla intencional (no se integra) para comprobar que CI queda en rojo; después cerrarlo.

## 9. Criterios de aceptación verificables

- Los cuatro repos tienen un workflow que corre en `pull_request` y `push` a `master`.
- El workflow del core corre las pruebas unitarias y las de PostgreSQL (las 67 omitidas hoy se ejecutan en CI).
- faclab-invoicing tiene `package-lock.json` versionado y no depende de `pettier`.
- Una prueba fallida deja el check en rojo (comprobado con un PR de prueba).
- El reporte de cobertura del core queda disponible como artefacto y su porcentaje se anota en CURRENT_STATE.md.

## 10. Pruebas que deben ejecutarse

- Ejecutar cada workflow en un PR real y revisar los logs de cada paso.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core
- faclab-infra: `docker compose config -q` y levantar los servicios afectados

## 11. Riesgos y posibles regresiones

- Las pruebas de PostgreSQL pueden depender del entorno Docker local (nombre de la base `_test`); adaptar `TEST_DATABASE_URL` al servicio de CI.
- Regenerar `package-lock.json` puede subir versiones transitivas; revisar el diff y correr todas las pruebas.
- Los finales de línea CRLF de `faclab-web/package.json` pueden romperse si se edita sin cuidado.

## Pendientes fuera de alcance

- **Protección de `master`:** la configura el usuario en cada repo (Settings → Branches o Rules). Debe
  exigir `lint` y `test` (core), `checks` (invoicing y web) y `validate` (infra), y no `e2e`. En una
  organización con plan gratuito, los repos privados (core, invoicing, web) no admiten protección de
  ramas ni rulesets; ahí el check queda solo como aviso.
- **G-60 (resto):** recrear el `.venv` local con Python 3.12; hoy usa 3.11 y su psycopg2 no enlaza con
  libpq. passlib sigue en S1.4.
- **PostgreSQL:** CI usa 17 y el `docker-compose.yml` del core usa 14. Alinear en S1.2 o S8.1.
- **Playwright:** generar las capturas de referencia de Linux para validar `visual.spec.ts` en CI.
  Volver bloqueante el job `e2e` cuando sea estable.
- **G-56 (resto):** los Dockerfiles de invoicing y web quedan en S1.3.
- **Dependencias vulnerables:** `npm audit` en invoicing reporta 67 vulnerabilidades (38 moderadas,
  25 altas, 4 críticas). No se tocaron porque están fuera de alcance, y ninguna sesión del roadmap cubre
  la auditoría de dependencias. Conviene asignarla, por ejemplo a S9.3, o agregar Dependabot en una
  sesión aparte.
- **Minutos de Actions:** el job `e2e` de web tarda unos 9 min por run en un repo privado. Si los minutos
  del plan gratuito no alcanzan, puede limitarse a `push` a `master` y `workflow_dispatch`.
