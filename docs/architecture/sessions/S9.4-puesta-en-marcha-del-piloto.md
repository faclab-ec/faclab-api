# S9.4 — Puesta en marcha del piloto

> **Estado:** pendiente · **Etapa 9 — Piloto y endurecimiento** · **Tamaño:** L · **Repos:** faclab-core, faclab-invoicing, faclab-web, faclab-infra · **Brechas:** —

## 1. Identificador y título

`S9.4` — Puesta en marcha del piloto

## 2. Objetivo verificable

La primera ferretería opera en producción: datos importados y validados con el cliente, certificado y ambiente de producción del SRI activos, usuarios capacitados, monitoreo reforzado y un plan de soporte durante las primeras semanas.

## 3. Problema que resuelve

El objetivo del roadmap es tener un cliente real usando el sistema con confianza.

## 4. Evidencia de la brecha actual

- Estado actual: solo desarrollo local (decisión del 2026-10-14).

## 5. Componentes y archivos que probablemente se modificarán

- Configuración de producción, datos del cliente, checklist de puesta en marcha en docs/architecture/.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- Todas las decisiones pendientes D-1 a D-9 resueltas; resultados de S9.1–S9.3.

## 7. Dependencias y sesiones previas

[S9.1](S9.1-e2e-flujo-completo.md), [S9.2](S9.2-carga-y-linea-base.md), [S9.3](S9.3-revision-de-seguridad.md), [S8.3](S8.3-respaldos-y-recuperacion.md), [S8.5](S8.5-onboarding-y-consola.md)

## 8. Tareas concretas en orden

1. Checklist previo: respaldos probados, alertas activas, dominios, certificados, decisiones legales confirmadas.
2. Importar y validar con el cliente catálogo, clientes, proveedores y saldos iniciales.
3. Configurar perfil fiscal, certificado, establecimientos, puntos de emisión y secuenciales iniciales; emitir una factura real controlada con el cliente.
4. Capacitación y material de ayuda.
5. Acompañamiento intensivo: revisión diaria de dashboards y conciliación durante las primeras semanas.

## 9. Criterios de aceptación verificables

- El cliente emite facturas autorizadas en producción y cuadra su primer cierre de caja con el sistema.
- Sin discrepancias de conciliación sin resolver al final de la primera semana.

## 10. Pruebas que deben ejecutarse

- Checklist de puesta en marcha completo y firmado por el usuario.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core
- faclab-infra: `docker compose config -q` y levantar los servicios afectados

## 11. Riesgos y posibles regresiones

- Datos del cliente con errores: validar la importación en staging primero.

## 12. Migraciones, cambios de configuración y despliegue

- Datos reales del cliente.

## 13. Estrategia de rollback o recuperación

- Plan de contingencia acordado con el cliente (por ejemplo, emisión desde el portal del SRI si el sistema falla).

## 14. Documentación que debe actualizarse

- Checklist y bitácora del piloto en docs/architecture/.

## 15. Condición para declarar la sesión terminada

- Todos los criterios de aceptación se cumplen y las pruebas listadas pasan (en CI si ya existe).
- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
