# S1.4 — Endurecimiento de seguridad del API y la sesión

> **Estado:** en curso (2026-10-15) · rama `fix/s1-4-seguridad-del-api` en faclab-core y faclab-web · completa y verificada localmente; falta CI verde en los PR para marcarla terminada · **Etapa 1 — Fundamentos** · **Tamaño:** M · **Repos:** faclab-core, faclab-web · **Brechas:** G-39, G-42, G-43, G-44, G-45, G-46, G-47

## 1. Identificador y título

`S1.4` — Endurecimiento de seguridad del API y la sesión

## 2. Objetivo verificable

Ningún campo de autoría se toma del cuerpo de la solicitud; el refresh token rota y su reutilización revoca la sesión; el login se bloquea tras intentos fallidos; las respuestas y los logs no exponen textos internos ni contraseñas; el frontend guarda el refresh token en una cookie HttpOnly y el access token en memoria.

## 3. Problema que resuelve

Hoy cualquiera con un token puede firmar operaciones de caja, devoluciones o ajustes a nombre de otra persona, un refresh token robado sirve durante 7 días, no hay protección contra fuerza bruta y una contraseña inválida puede terminar en los logs.

## 4. Evidencia de la brecha actual

- `created_by`, `cashier_name`, `performed_by`, `refunded_by`, `adjusted_by`, `requested_by` vienen del cuerpo (`src/pos/sales/infra/validators.py:69-73`, `src/pos/cash/infra/validators.py:16-20`, `src/pos/refund/infra/validators.py:37-41`, `src/inventory/adjustment/app/commands/adjustment.py:35`) (G-39).
- `src/auth/app/commands/refresh_token.py:32-51`: emite un par nuevo pero el refresh anterior sigue siendo válido (G-43).
- Sin bloqueo de login ni rate limiting (G-42); login sin hash para usuarios inexistentes (`login.py:39-43`) (G-47).
- `src/shared/infra/middlewares.py:188-195` devuelve el texto de `ValueError`; `token_service.py:80` devuelve el texto de PyJWT (G-45).
- `middlewares.py:127` registra `str(exc)` de la validación, con el `input` de cada error (G-46).
- `faclab-web/src/shared/lib/auth/tokenStorage.ts` guarda ambos tokens en `localStorage` (G-44).

- faclab-core: `src/auth/` (rotación de refresh con `jti` o contador en `auth_sessions`, detección de reutilización, bloqueo progresivo por usuario e IP, hash ficticio para usuarios inexistentes, endpoints que leen y escriben la cookie de refresh).

- faclab-web: `src/shared/lib/auth/*`, `httpClient.ts`, `useAuth.ts` (access token en memoria, refresh por cookie con `withCredentials`, sincronización entre pestañas con BroadcastChannel).

## 8. Tareas concretas en orden

1. Listar todos los campos de autoría que llegan en cuerpos de solicitud (buscar `_by`, `cashier_name`, `user`) y reemplazarlos por el usuario autenticado; mantener el nombre visible guardado en el documento para recibos.
2. Implementar rotación del refresh token: cada refresh invalida el anterior; si se presenta uno ya usado, revocar la sesión completa y responder 401 `TOKEN_REUSED`.
3. Entregar el refresh token en una cookie `HttpOnly; Secure; SameSite=Strict; Path=/api/auth` (en local sin `Secure`), manteniendo el cuerpo de respuesta compatible durante la transición solo si el usuario lo pide.
4. Agregar bloqueo progresivo de login (por ejemplo, 5 fallos en 15 min bloquean 15 min por usuario; límite por IP) con error `LOGIN_LOCKED` y hash ficticio para usuarios inexistentes.
5. Cambiar los mensajes de `ValueError` y de JWT a textos genéricos con código estable; registrar el detalle solo en el log del servidor.
6. Quitar `input` de los errores de validación que se registran y agregar un procesador de redacción mínimo para claves sensibles (se completa en S1.5).
7. Agregar cabeceras `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` y un límite de tamaño de cuerpo.
8. Frontend: mover el access token a memoria, usar la cookie para refrescar, sincronizar logout y refresh entre pestañas, y mostrar el mensaje de bloqueo de login.
9. Actualizar las pruebas existentes de auth, POS y ajustes y agregar las nuevas.

## 9. Criterios de aceptación verificables

- Ningún validador de entrada contiene campos de autoría; los documentos guardan el usuario autenticado (prueba que envía un nombre falso y verifica que se ignora).
- Usar dos veces el mismo refresh token revoca la sesión (prueba de integración).
- Tras N intentos fallidos el login responde `LOGIN_LOCKED` aunque la contraseña sea correcta, hasta que pasa el tiempo de bloqueo.
- Una solicitud con contraseña corta en `change-password` no deja la contraseña en el log capturado por la prueba.
- El frontend no guarda tokens en `localStorage` (prueba unitaria) y el flujo de login, refresh y logout funciona en el navegador.
- faclab-invoicing sigue validando los access tokens del core.

## 11. Riesgos y posibles regresiones

- Cambiar el almacenamiento de tokens cierra las sesiones abiertas; aceptable en desarrollo.
- La cookie entre dominios distintos (web y API) exige configurar CORS con credenciales y `SameSite` adecuado; si web y API quedan en subdominios distintos, revisar `SameSite=Lax` o un mismo sitio.
- Quitar campos del cuerpo rompe clientes que los envían: el frontend debe actualizarse en la misma entrega.

## 12. Migraciones, cambios de configuración y despliegue

- Migración Alembic para los campos de rotación en `auth_sessions` y el registro de intentos de login.
- Variables nuevas: parámetros de bloqueo y dominio de la cookie.
- Desplegar core y web juntos.

## 13. Estrategia de rollback o recuperación

- Revertir core y web juntos; la migración agrega columnas nulas o tablas nuevas, así que el `downgrade` es seguro.

## Avance (2026-10-15)

Ramas `fix/s1-4-seguridad-del-api` en faclab-core (commits `a6a01d3`, `28746c5` y el de cierre) y faclab-web (`3c3885b`, `46f09c7`, `82df5b7`). faclab-invoicing no cambia.

Decisiones tomadas con el usuario:

- **Autor visible:** nombre completo del usuario y, si no tiene, su username. Se agregó `users.full_name` (opcional, máximo 64 para caber en las columnas de autor), editable al crear el usuario y con `PUT /api/admin/users/{id}/profile`; el access token lo lleva en el claim `name`. No se guarda el id del autor en los documentos (queda para S3.5).
- **Reutilización del refresh:** gracia de 30 s (`JWT_REFRESH_REUSE_GRACE_SECONDS`) para el token recién reemplazado, que recibe el token vigente sin volver a rotar; cualquier otro ya usado revoca la sesión (`TOKEN_REUSED`).
- **Sin modo de transición:** `refreshToken` ya no va en ningún cuerpo; core y web se despliegan juntos.

Qué cambió:

- **Autoría (G-39):** turnos, ventas POS (normal y rápida), movimientos de caja, devoluciones, ajustes y transferencias toman el autor de `get_current_user`. Ningún validador de entrada tiene campos de autoría (`tests/integration/auth/test_no_author_fields_in_requests.py` lo exige). Editar un ajuste o una transferencia ya no cambia su autor. Se quitó el `created_by` muerto de `SaleRequest`.
- **Refresh (G-43, G-44):** cookie `faclab_refresh` (`HttpOnly`, `SameSite=Strict`, `Path=/api/auth`, `Secure` fuera de local) en login y refresh; logout la borra. Rotación con `jti` y columnas `refresh_jti`, `previous_refresh_jti`, `refreshed_at` en `auth_sessions`; la fila se bloquea (`FOR UPDATE`) para serializar refresh concurrentes.
- **Errores que conservan cambios:** `BaseError.commit_transaction` hace que la sesión de la solicitud confirme lo escrito antes del error (intento fallido de login, revocación por reutilización).
- **Bloqueo de login (G-42, G-47):** tabla `login_failures`; 5 fallas en 15 min bloquean el usuario y 20 la IP durante 15 min (configurable), 429 `LOGIN_LOCKED` aunque la contraseña sea correcta. Usuarios inexistentes gastan un bcrypt ficticio y también se bloquean.
- **Mensajes y logs (G-45, G-46):** errores de PyJWT y `ValueError` inesperados responden texto genérico; los value objects lanzan `InvalidValueError` (sigue siendo `ValueError`) y conservan su mensaje. El log de validación ya no lleva `input` y el procesador `redact_sensitive` enmascara contraseñas, tokens, secretos y cookies.
- **Cabeceras y cuerpo:** `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` y 413 `REQUEST_TOO_LARGE` sobre `MAX_REQUEST_BODY_BYTES` (1 MiB).
- **Web:** access token en memoria, refresh por cookie con `withCredentials` solo en login, refresh y logout; restauración de sesión al cargar (marca `fc.hasSession`), refresh proactivo también tras recargar, sincronización de tokens y logout entre pestañas con `BroadcastChannel`, mensaje de bloqueo en el login, formularios sin autor y nombre completo en la gestión de usuarios.
- **Migración** `f310fe129c85` (columnas nulas y tabla nueva; `downgrade` simétrico). Variables nuevas: `AUTH_COOKIE_SECURE`, `AUTH_COOKIE_DOMAIN`, `JWT_REFRESH_REUSE_GRACE_SECONDS`, `LOGIN_MAX_FAILURES_PER_USER`, `LOGIN_MAX_FAILURES_PER_IP`, `LOGIN_FAILURE_WINDOW_SECONDS`, `LOGIN_LOCKOUT_SECONDS`, `MAX_REQUEST_BODY_BYTES`.

## Pendientes fuera de alcance

- Guardar el id del autor (no solo el nombre) en los documentos y registrar quién aprueba o procesa una devolución: S3.5 (bitácora de auditoría).
- El access token sigue siendo válido hasta 15 min después de logout o revocación, porque no se consulta la sesión en cada petición.
- Límite general de solicitudes del API (no solo login): S6.3.
- Cambiar el rol de un usuario no revoca sus sesiones; sus tokens conservan los permisos anteriores hasta el siguiente refresh.
- Política completa de redacción de logs, incluido el texto de `IntegrityError` y de excepciones registradas: S1.5.
- Cabeceras de seguridad del frontend (CSP, HSTS) en Caddy o el proxy de entrada: S8.1.
- Con la cookie `SameSite=Strict`, web y API deben estar en el mismo sitio (p. ej. `app.` y `api.` del mismo dominio, decisión D-9); con dominios distintos habría que pasar a `Lax` y revisar CSRF.
