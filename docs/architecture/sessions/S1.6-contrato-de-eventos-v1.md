# S1.6 — Contrato de eventos v1 y pruebas de contrato

> **Estado:** pendiente · **Etapa 1 — Fundamentos** · **Tamaño:** M · **Repos:** faclab-core, faclab-invoicing · **Brechas:** G-08, G-76

## 1. Identificador y título

`S1.6` — Contrato de eventos v1 y pruebas de contrato

## 2. Objetivo verificable

Los mensajes `sales.confirmed` e `invoices` tienen JSON Schema versionado en `faclab-core/contracts/events/`; el CI del core valida lo que produce y el de invoicing valida sus esquemas zod contra los mismos ejemplos; una venta con cliente sin email, teléfono o dirección se factura.

## 3. Problema que resuelve

El core envía campos nulos que facturación rechaza: esas ventas van a la cola de mensajes fallidos y nunca se facturan. No hay versión ni pruebas que detecten incompatibilidades.

## 4. Evidencia de la brecha actual

- `src/invoicing/infra/event_handlers.py:42-50` envía `email`, `phone`, `address` posiblemente nulos; `faclab-invoicing/src/modules/invoice/infra/messaging/schemas.ts:23-25` los exige como string (G-08).
- `sku` y `product_name` nulos si falta el producto (`event_handlers.py:76-77`).
- Sin `schema_version` en ninguno de los dos lados; sin pruebas cruzadas (G-76).

## 5. Componentes y archivos que probablemente se modificarán

- faclab-core: `contracts/events/sales.confirmed/v1.schema.json`, `contracts/events/invoices/v1.schema.json`, ejemplos válidos y casos límite en `contracts/events/*/examples/`.
- faclab-core: `src/invoicing/infra/event_handlers.py` (agregar `schema_version: 1` al envelope, sin cambiar el resto) y prueba que valida los mensajes producidos contra el esquema.
- faclab-invoicing: `src/modules/invoice/infra/messaging/schemas.ts` (campos opcionales y nulos según el contrato; defaults del SRI para cliente sin datos de contacto), `invoice-xml-builder.ts` (no escribir `infoAdicional` vacío), prueba de contrato que lee los ejemplos.
- CI de ambos repos (paso de contrato).

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- faclab-core: `src/invoicing/` completo, `src/shared/infra/outbox/writer.py`, `tests/unit/invoicing/test_sale_confirmed_message.py`.
- faclab-invoicing: `schemas.ts`, `receive-sale.ts`, `prepare-invoice.ts`, `invoice-xml-builder.ts`, `src/modules/invoice/domain/events.ts`.
- Ficha técnica del SRI vigente para los campos obligatorios de comprador y la sección `infoAdicional`.

## 7. Dependencias y sesiones previas

[S1.1](S1.1-ci-minima.md)

## 8. Tareas concretas en orden

1. Documentar el contrato actual campo por campo (tipo, nulabilidad, formato de montos) a partir del productor real del core.
2. Escribir los JSON Schema v1 de `sales.confirmed` y de `invoices`, incluyendo `schema_version` y ejemplos: venta con cliente completo, cliente sin email ni teléfono ni dirección, consumidor final, producto sin SKU.
3. Core: agregar `schema_version: 1` y una prueba que genere mensajes con los handlers reales y los valide contra el esquema (biblioteca `jsonschema` como dependencia de desarrollo).
4. Invoicing: alinear zod con el contrato (nulos permitidos donde el contrato los permite), usar los valores por defecto que exige el SRI cuando falten datos de contacto, y agregar una prueba que valide cada ejemplo con zod y genere el XML.
5. Definir cómo invoicing obtiene los ejemplos del core en CI (copia fijada por commit o checkout del repo del core en una versión fija) y documentar la política de compatibilidad.
6. Agregar los pasos de contrato al CI de ambos repos.

## 9. Criterios de aceptación verificables

- Los esquemas y ejemplos existen y el CI de ambos repos los valida.
- Un ejemplo de cliente sin email, teléfono ni dirección pasa la validación de invoicing y produce un XML válido.
- Si alguien cambia el productor del core de forma incompatible, la prueba de contrato del core falla.
- La política de compatibilidad (ADR-0006) está reflejada en `contracts/README.md`.

## 10. Pruebas que deben ejecutarse

- Pruebas de contrato nuevas en ambos repos.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`

## 11. Riesgos y posibles regresiones

- Volver opcionales campos que el XML usa puede producir XML inválido: cubrir con la prueba de generación de XML.
- Desfase de versiones entre repos: desplegar invoicing (acepta ambos) antes que el core.

## 12. Migraciones, cambios de configuración y despliegue

- Sin migraciones. Orden de despliegue: invoicing primero, core después.

## 13. Estrategia de rollback o recuperación

- Revertir el core primero y luego invoicing; el campo `schema_version` es aditivo.

## 14. Documentación que debe actualizarse

- README de faclab-invoicing (contrato consumido) y docs/architecture.md del core (sección Kafka).
