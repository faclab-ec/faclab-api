# S8.2 — Entrega continua y versionado coordinado

> **Estado:** pendiente · **Etapa 8 — SaaS y producción** · **Tamaño:** M · **Repos:** faclab-core, faclab-invoicing, faclab-web, faclab-infra · **Brechas:** G-57

## 1. Identificador y título

`S8.2` — Entrega continua y versionado coordinado

## 2. Objetivo verificable

Al etiquetar una versión semántica, el CI de cada repo publica su imagen en GitHub Container Registry con `service.version`; un workflow de despliegue aplica migraciones, actualiza los servicios en orden y verifica `/health/ready`; una matriz de compatibilidad documenta qué versiones funcionan juntas; revertir a la versión anterior es un comando.

## 3. Problema que resuelve

Sin tags ni imágenes versionadas, desplegar y revertir es manual y propenso a incompatibilidades.

## 4. Evidencia de la brecha actual

- 0 tags en los cuatro repos; versiones fijas en el código (G-57).

## 5. Componentes y archivos que probablemente se modificarán

- Workflows de release en cada repo, workflow de despliegue en faclab-infra, `deploy/versions.env` (versiones en producción), CHANGELOG por repo.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- CI existente (S1.1), compose de producción (S8.1), contratos (`contracts/`) para la matriz.

## 7. Dependencias y sesiones previas

[S8.1](S8.1-stack-de-produccion-en-vps.md), [S1.1](S1.1-ci-minima.md)

## 8. Tareas concretas en orden

1. Adoptar versionado semántico y CHANGELOG en cada repo (convención de commits existente).
2. Publicar imágenes al crear un tag, con `SERVICE_VERSION` inyectado.
3. Workflow de despliegue por SSH: respaldo previo, migraciones, actualización en orden (infra → invoicing → core → web), verificación de salud y reversión automática si falla.
4. Matriz de compatibilidad basada en las versiones de contratos.
5. Documentar la reversión (incluidas migraciones no reversibles).

## 9. Criterios de aceptación verificables

- Un tag produce una imagen versionada en el registro.
- Un despliegue a staging con una versión rota se revierte solo y queda la anterior funcionando.

## 10. Pruebas que deben ejecutarse

- Despliegues de prueba en staging.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core
- faclab-infra: `docker compose config -q` y levantar los servicios afectados

## 11. Riesgos y posibles regresiones

- Migraciones irreversibles: el workflow exige respaldo previo.

## 12. Migraciones, cambios de configuración y despliegue

- Secretos de despliegue en GitHub (llave SSH limitada).

## 13. Estrategia de rollback o recuperación

- Volver a desplegar el tag anterior con el mismo workflow.

## 14. Documentación que debe actualizarse

- README de cada repo (release), guía de despliegue en faclab-infra, ROADMAP.md.

## 15. Condición para declarar la sesión terminada

- Todos los criterios de aceptación se cumplen y las pruebas listadas pasan (en CI si ya existe).
- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
