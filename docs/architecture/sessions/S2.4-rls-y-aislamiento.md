# S2.4 — Row-Level Security y pruebas negativas de aislamiento

> **Estado:** pendiente · **Etapa 2 — Multiempresa y multisucursal** · **Tamaño:** M · **Repos:** faclab-core · **Brechas:** G-01

## 1. Identificador y título

`S2.4` — Row-Level Security y pruebas negativas de aislamiento

## 2. Objetivo verificable

Todas las tablas de negocio tienen RLS activo y forzado; el API se conecta con un rol que no puede saltarse RLS; una suite recorre todas las rutas de `main.app` y demuestra que ninguna devuelve ni modifica datos de otra empresa.

## 3. Problema que resuelve

El filtro en la aplicación puede olvidarse en una consulta nueva; la base de datos debe impedir el acceso cruzado aunque el código falle.

## 4. Evidencia de la brecha actual

- Las consultas de reportes, recibos y caja leen modelos directamente desde la capa de aplicación (CLAUDE.md, Module boundaries).
- No existen roles de base de datos separados; la aplicación usa el dueño de las tablas.

## 5. Componentes y archivos que probablemente se modificarán

- Migración con `ENABLE` y `FORCE ROW LEVEL SECURITY` y políticas por tabla; roles `faclab_owner`, `faclab_app`, `faclab_worker`.
- `config/` y compose: `DATABASE_URL` (app), `DATABASE_URL_MIGRATIONS` (owner), `DATABASE_URL_WORKER`.
- `alembic/env.py` (usar la conexión de migraciones).
- Relay del outbox y tareas de plataforma: usar el rol `faclab_worker`.
- `tests/integration/postgres/test_tenant_isolation.py` (nuevo) y fixtures de dos empresas.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- `tests/integration/auth/test_all_*_routes_require_auth.py` (patrón para recorrer rutas).
- `tests/integration/postgres/conftest.py` y `api.py` (helpers y factories).
- Script de inicialización de la base en compose y CI.

## 7. Dependencias y sesiones previas

[S2.3](S2.3-tenant-id-en-modulos.md)

## 8. Tareas concretas en orden

1. Crear los roles y permisos (`GRANT`) en una migración o script de inicialización idempotente.
2. Activar y forzar RLS con la política `tenant_id = current_setting('app.tenant_id', true)::uuid` en cada tabla de negocio; dejar `outbox_messages` y `dead_letters` sin RLS pero accesibles solo para `faclab_worker` y `faclab_app` (inserción).
3. Separar las cadenas de conexión por rol y usar el rol correcto en API, worker y migraciones.
4. Escribir la suite de aislamiento: por cada ruta, crear recursos en la empresa B y llamar con un token de la empresa A esperando 404/422, y verificar que los listados no contienen ids de B.
5. Agregar pruebas directas en SQL: sin contexto no hay filas; con contexto A no se ven filas de B; un `INSERT` con `tenant_id` de B falla.
6. Agregar al CI la suite de aislamiento como obligatoria.

## 9. Criterios de aceptación verificables

- Con el rol `faclab_app`, `SELECT * FROM products` sin `app.tenant_id` devuelve 0 filas (prueba).
- Ninguna ruta de `main.app` devuelve datos de otra empresa (suite que falla si se agrega una ruta sin cubrir).
- El relay del outbox sigue publicando mensajes de todas las empresas.
- Las migraciones corren con el rol dueño y el API con el rol de aplicación.

## 10. Pruebas que deben ejecutarse

- Suite de aislamiento nueva y pruebas SQL de RLS (PostgreSQL).
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL

## 11. Riesgos y posibles regresiones

- Una tarea que no establece contexto dejará de ver datos (falla cerrada): revisar el seed, la CLI de alta y los scripts.
- RLS agrega un predicado a cada consulta: verificar que los índices empiecen por `tenant_id`.

## 12. Migraciones, cambios de configuración y despliegue

- Migración de RLS y roles; variables nuevas de conexión por rol.
- En el VPS, crear los roles antes de desplegar (documentar en S8.1).

## 13. Estrategia de rollback o recuperación

- Migración `downgrade` que desactiva RLS; volver a una sola cadena de conexión.

## 14. Documentación que debe actualizarse

- docs/architecture/MULTI_TENANCY.md §6 y §8, ADR-0002 (aceptado).
- CLAUDE.md del core (variables de conexión, regla: toda tabla nueva lleva política RLS y entra en la suite de aislamiento).

## 15. Condición para declarar la sesión terminada

- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
