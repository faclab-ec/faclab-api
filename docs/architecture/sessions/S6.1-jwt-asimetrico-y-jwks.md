# S6.1 — Firma asimétrica de tokens y JWKS

> **Estado:** pendiente · **Etapa 6 — API pública** · **Tamaño:** M · **Repos:** faclab-core, faclab-invoicing · **Brechas:** G-48

## 1. Identificador y título

`S6.1` — Firma asimétrica de tokens y JWKS

## 2. Objetivo verificable

El core firma los tokens con una clave privada (EdDSA o RS256), publica las claves públicas en `/.well-known/jwks.json` con `kid` y soporta rotación con dos claves activas; faclab-invoicing valida con JWKS y ya no conoce ningún secreto capaz de emitir tokens.

## 3. Problema que resuelve

Facturación valida con el mismo secreto HS256 con que se firma: si se compromete, puede emitir tokens válidos para el core.

## 4. Evidencia de la brecha actual

- `src/auth/infra/token_service.py:17` usa HS256 con `JWT_SECRET`.
- `faclab-invoicing/src/shared/infra/http/auth.ts:45-109` valida HS256 con el mismo secreto (G-48).

## 5. Componentes y archivos que probablemente se modificarán

- Core: `token_service.py` (algoritmo asimétrico, `kid`, carga de claves desde archivos o variables), endpoint JWKS público, rotación documentada.
- Invoicing: `auth.ts` (validación con JWKS cacheado, verificación de `iss`, `aud` y `kid`).
- Configuración y secretos en ambos.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- `src/auth/infra/token_service.py` y pruebas; `faclab-invoicing/src/shared/infra/http/auth.ts` y su configuración.

## 7. Dependencias y sesiones previas

[S2.1](S2.1-tenants-y-membresias.md)

## 8. Tareas concretas en orden

1. Elegir el algoritmo (EdDSA si las bibliotecas de ambos lados lo soportan; si no, RS256) y documentar la decisión.
2. Cargar claves privadas desde secretos y exponer JWKS con las públicas activas.
3. Agregar `aud` a los tokens (`faclab-core`, `faclab-invoicing`) y validarlo.
4. Invoicing: validar con JWKS cacheado (refresco periódico y ante `kid` desconocido).
5. Procedimiento de rotación: agregar clave nueva, firmar con ella, retirar la anterior tras el TTL del refresh.
6. Eliminar `JWT_SECRET` de invoicing.

## 9. Criterios de aceptación verificables

- Un token firmado con una clave que no está en el JWKS es rechazado por ambos servicios (prueba).
- La rotación con dos claves activas no invalida sesiones vigentes (prueba).
- Invoicing no tiene ninguna variable de secreto JWT.

## 10. Pruebas que deben ejecutarse

- Pruebas de token y JWKS en core; pruebas del guard en invoicing.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`

## 11. Riesgos y posibles regresiones

- Cambiar el algoritmo invalida todas las sesiones al desplegar: aceptable fuera de producción o planificar ventana.

## 12. Migraciones, cambios de configuración y despliegue

- Claves nuevas en el gestor de secretos; despliegue core → invoicing.

## 13. Estrategia de rollback o recuperación

- Volver a HS256 con el secreto anterior (mantenerlo durante una versión).
