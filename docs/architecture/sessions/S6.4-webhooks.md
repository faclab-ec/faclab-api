# S6.4 — Webhooks firmados

> **Estado:** pendiente · **Etapa 6 — API pública** · **Tamaño:** M · **Repos:** faclab-core · **Brechas:** G-72

## 1. Identificador y título

`S6.4` — Webhooks firmados

## 2. Objetivo verificable

Una empresa registra endpoints HTTPS con eventos elegidos; los eventos se encolan en la misma transacción, el worker los entrega firmados (Standard Webhooks) con reintentos y desactivación por fallos, y hay historial, evento de prueba y reenvío manual.

## 3. Problema que resuelve

Las integraciones tendrían que consultar la API constantemente para enterarse de ventas, stock y facturas.

## 4. Evidencia de la brecha actual

- No existe ningún mecanismo de notificación saliente (G-72).

## 5. Componentes y archivos que probablemente se modificarán

- `src/integrations/webhooks/` (endpoints, suscripciones, entregas, firma), suscriptores de eventos de dominio, tarea del worker, endpoints de administración.
- Protección contra SSRF, es decir, que el servidor sea usado para llamar a recursos internos (solo HTTPS, bloqueo de IP privadas y locales tras resolver DNS).

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- Bus de eventos y outbox (S3.4), eventos de dominio existentes, resultados de facturación (`invoice_status`).

## 7. Dependencias y sesiones previas

[S6.2](S6.2-credenciales-de-integracion.md), [S3.4](S3.4-worker-y-mensajeria-resiliente.md)

## 8. Tareas concretas en orden

1. Definir los contratos públicos v1 de cada tipo de evento (PUBLIC_API.md §7) con JSON Schema.
2. Crear las entregas en la misma transacción del evento de dominio; agrupar `stock.changed`.
3. Implementar el envío firmado con timeout, backoff y desactivación tras fallos sostenidos (con aviso).
4. Implementar `excludeOwnChanges` y el campo de origen en escrituras de integraciones.
5. Historial de 30 días, evento de prueba y reenvío manual.
6. Pruebas con un receptor local que verifica firmas.

## 9. Criterios de aceptación verificables

- Un receptor que valida la firma con el ejemplo de PUBLIC_API.md acepta los eventos (prueba).
- Un endpoint caído recibe reintentos y se desactiva tras el umbral; al reactivarlo se pueden reenviar entregas.
- Una URL que resuelve a una IP privada se rechaza.

## 10. Pruebas que deben ejecutarse

- Pruebas unitarias de firma, integración del worker con receptor local, pruebas de SSRF.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL

## 11. Riesgos y posibles regresiones

- Un receptor lento no debe frenar al worker: concurrencia limitada por endpoint.

## 12. Migraciones, cambios de configuración y despliegue

- Tablas nuevas con RLS.

## 13. Estrategia de rollback o recuperación

- Pausar las entregas por configuración; las pendientes se conservan.

## 14. Documentación que debe actualizarse

- PUBLIC_API.md §7, guía de webhooks para integradores.

## 15. Condición para declarar la sesión terminada

- Todos los criterios de aceptación se cumplen y las pruebas listadas pasan (en CI si ya existe).
- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
