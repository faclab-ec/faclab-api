# S6.3 — API pública `/api/v1` y límites de solicitudes

> **Estado:** pendiente · **Etapa 6 — API pública** · **Tamaño:** L · **Repos:** faclab-core, faclab-invoicing · **Brechas:** G-72, G-73, G-42

## 1. Identificador y título

`S6.3` — API pública `/api/v1` y límites de solicitudes

## 2. Objetivo verificable

Existe el catálogo inicial de PUBLIC_API.md §5 bajo `/api/v1` con modelos propios, paginación con orden estable, filtros, `sort`, dinero y cantidades como strings, `Idempotency-Key` en creaciones, límites de solicitudes con encabezados estándar y un OpenAPI público separado que el CI compara contra la versión anterior.

## 3. Problema que resuelve

Las integraciones necesitan un contrato estable que no cambie con el frontend.

## 4. Evidencia de la brecha actual

- Solo existen `/api/admin`, `/api/pos` y `/api/auth` (G-72).
- Listados sin orden estable ni parámetros de ordenamiento (G-73).

## 5. Componentes y archivos que probablemente se modificarán

- Core: `src/public_api/` (routers y esquemas públicos que llaman a comandos y consultas existentes), OpenAPI público, middleware de límites (almacén según D-6).
- Invoicing: `/api/v1/invoices` (listado, detalle, XML, RIDE) validando tokens por JWKS y scopes.
- Caddy o compose: enrutamiento de `/api/v1/invoices*`.
- CI: comparación de OpenAPI (por ejemplo `oasdiff`).

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- Comandos y consultas existentes que se reutilizarán; `src/shared/infra/validators.py` (envelope); PUBLIC_API.md completo.

## 7. Dependencias y sesiones previas

[S6.2](S6.2-credenciales-de-integracion.md), [S3.1](S3.1-idempotencia.md)

## 8. Tareas concretas en orden

1. Definir los esquemas públicos de cada recurso del catálogo inicial (sin reutilizar validadores internos).
2. Implementar los routers llamando a comandos y consultas existentes; ventas de canal `api` con sucursal y punto de emisión.
3. Agregar paginación con orden estable, `updatedSince`, filtros y `sort` con lista blanca.
4. Implementar los límites de solicitudes por cliente y por empresa con encabezados `RateLimit-*` y 429.
5. Generar el OpenAPI público y agregar al CI la comparación con la versión publicada.
6. Exponer el endpoint de comprobantes en invoicing con los mismos principios.
7. Probar el catálogo completo con un cliente de integración y la suite de aislamiento.

## 9. Criterios de aceptación verificables

- Cada endpoint del catálogo inicial existe, está documentado y tiene pruebas de permisos y aislamiento.
- Ningún endpoint público expone campos internos no documentados (prueba que compara la respuesta con el esquema).
- Superar el límite devuelve 429 con `Retry-After`.
- Un cambio incompatible en el OpenAPI público hace fallar el CI.

## 10. Pruebas que deben ejecutarse

- Pruebas de integración por endpoint, de límites y de compatibilidad de OpenAPI.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`

## 11. Riesgos y posibles regresiones

- Reutilizar comandos internos puede filtrar errores internos: mapear a códigos del catálogo público.

## 12. Migraciones, cambios de configuración y despliegue

- Almacén de límites (Redis o tabla) según D-6; rutas nuevas en el proxy.

## 13. Estrategia de rollback o recuperación

- Desactivar `/api/v1` por configuración.

## 14. Documentación que debe actualizarse

- PUBLIC_API.md, changelog público, `docs/public-api/` con guías.

## 15. Condición para declarar la sesión terminada

- Todos los criterios de aceptación se cumplen y las pruebas listadas pasan (en CI si ya existe).
- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
