# S9.8 — Cadena de suministro y secretos

> **Estado:** pendiente · **Etapa 9 — Piloto y endurecimiento** · **Tamaño:** L · **Repos:** faclab-infra, faclab-core, faclab-invoicing, faclab-web · **Brechas:** G-87, G-49

## 1. Identificador y título

`S9.8` — Cadena de suministro y secretos

## 2. Objetivo verificable

Las imágenes se publican firmadas (cosign keyless) con su SBOM y procedencia, el despliegue verifica la firma antes de usarlas, las imágenes base y de terceros van por digest y al día, Python tiene un lock con hashes, los secretos del servidor llegan como archivos y el Collector ya no puede leer el entorno de los contenedores; el tráfico interno sensible usa TLS.

## 3. Problema que resuelve

La revisión S9.3 dejó medios en la cadena de suministro y en los secretos: hoy el servidor confía en el digest que tenga el tag al desplegar, la mayoría de secretos son variables visibles con `docker inspect` (y para el Collector), y PostgreSQL, Kafka, el JWKS y OTLP viajan en claro por las redes internas.

## 4. Evidencia de la brecha actual

- S-23: el Collector lee el `Env` de todos los contenedores por el socket proxy (`deploy/production/compose.yaml`).
- S-24: sin TLS interno ni SASL en Kafka (G-49).
- S-25: sin firma ni verificación de imágenes; bases por tag; Python sin lock.
- S-28: cp-kafka (7.9.11: 5 altas en sus herramientas de Python) y docker-socket-proxy v0.5.0 (9 altas; 3.4 sale limpia).
- S-40: dumps previos al despliegue sin cifrar; S-41: tareas del compose sin `no-new-privileges`.
- Base Debian 12: ~100 altas sin arreglo; Debian 13 las baja a la mitad (SEGURIDAD.md §4.2).

## 5. Componentes y archivos que probablemente se modificarán

- faclab-infra: deploy/production (compose, stack.sh, deploy.sh, versions), workflows de release y deploy
- Dockerfiles y release.yml de los cuatro repos
- faclab-core: requirements con hashes (pip-tools o uv), Makefile
- config de los servicios para leer secretos `_FILE`

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- deploy/production/README.md, RESPALDOS.md, scripts/stack.sh, remote.sh
- los cuatro release.yml (S8.2) y security.yml (S9.3)
- config/ de core y src/config de invoicing (variables `_FILE`)

## 7. Dependencias y sesiones previas

[S9.3](S9.3-revision-de-seguridad.md), [S8.2](S8.2-entrega-continua.md)

## 8. Tareas concretas en orden

1. Firma cosign keyless, SBOM y procedencia en los cuatro release.yml; `deploy.sh`/`stack.sh` verifican la firma y la identidad del workflow antes de usar un digest.
2. Imágenes base por digest con Dependabot `docker`; core e invoicing a Debian 13; Kafka y el socket proxy a versiones sin altas, con la matriz de COMPATIBILITY.md.
3. Lock de Python con hashes (`pip install --require-hashes` en el Dockerfile) y el escaneo de dependencias sobre él.
4. Secretos como archivos (`_FILE`) para las URLs de base, llaves de almacenamiento, SMTP y la llave de certificados; el Collector sin acceso a `Env` (otro proxy o receptor sin inspect).
5. TLS en PostgreSQL (`sslmode=verify-full` con CA interna) y el JWKS por HTTPS o red dedicada; Kafka con SASL/TLS o anotado como riesgo aceptado mientras sea un solo nodo interno.
6. Dumps previos al despliegue cifrados y `no-new-privileges`/`cap_drop` en todas las tareas.

## 9. Criterios de aceptación verificables

- Un despliegue con una imagen sin firma o de otro workflow falla.
- `docker inspect` de los servicios no muestra secretos.
- El job `third-party-images` sin altas con arreglo.
- ASVS 12.3.x, 13.3.x y 15.1.2 actualizados en ASVS.md.

## 10. Pruebas que deben ejecutarse

- Las pruebas nuevas de cada tarea.
- Despliegue completo en staging con verificación de firmas y una reversión.
- `deploy/production/drill` (restauración) con el cambio de secretos.
- faclab-infra: `docker compose config -q`, `deploy/production/scripts/ci-validate.sh` y levantar los servicios afectados
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test` (y `test/postgres` con `TEST_DATABASE_URL`)
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core

## 11. Riesgos y posibles regresiones

- La verificación de firma puede bloquear un despliegue urgente: documentar el procedimiento de emergencia.
- TLS interno y secretos `_FILE` cambian el arranque de los cuatro servicios.
- Debian 13 y Kafka nuevo pueden cambiar comportamiento: e2e completo (faclab-infra/e2e/run.sh).

## 12. Migraciones, cambios de configuración y despliegue

- Variables `_FILE` nuevas en los cuatro servicios; secrets.env del servidor reorganizado.
- COMPATIBILITY.md con la versión mínima que verifica firmas.

## 13. Estrategia de rollback o recuperación

- `IMAGES_VERIFY=off` temporal en el servidor documentado.
- Las variables sin `_FILE` siguen funcionando durante la transición.
