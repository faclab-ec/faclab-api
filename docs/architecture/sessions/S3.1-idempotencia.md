# S3.1 — Idempotencia de comandos con `Idempotency-Key`

> **Estado:** pendiente · **Etapa 3 — Integridad transaccional** · **Tamaño:** M · **Repos:** faclab-core, faclab-web · **Brechas:** G-26

## 1. Identificador y título

`S3.1` — Idempotencia de comandos con `Idempotency-Key`

## 2. Objetivo verificable

Los POST que crean documentos o mueven dinero en el POS (venta rápida, confirmación, pagos, devoluciones, movimientos de caja) aceptan `Idempotency-Key`; repetir la solicitud con la misma clave devuelve la misma respuesta sin duplicar efectos; el frontend envía la clave y la reutiliza en los reintentos.

## 3. Problema que resuelve

Si la red falla después de confirmar una venta y el POS reintenta, se duplican la venta, el descuento de stock y el pago.

## 4. Evidencia de la brecha actual

- Ningún endpoint lee `Idempotency-Key` (búsqueda sin resultados) (G-26).

## 5. Componentes y archivos que probablemente se modificarán

- `src/shared/infra/idempotency.py` (nuevo): tabla `idempotency_keys (tenant_id, key, method, path, request_hash, status, response, created_at)` y dependencia de FastAPI.
- Rutas POS de ventas, pagos, devoluciones y caja.
- faclab-web: `httpClient.ts` y hooks del POS (generar clave por intención de operación y reutilizarla).
- Migración y tarea de limpieza (más de 24 h).

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- `src/pos/**/infra/routes.py`, `src/shared/infra/database.py` (commit al final del request), `src/shared/infra/middlewares.py`.
- `faclab-web/src/features/pos/` (envío de ventas y pagos) y `httpClient.ts` (reintentos).

## 7. Dependencias y sesiones previas

[S2.6](S2.6-pos-por-terminal.md)

## 8. Tareas concretas en orden

1. Diseñar el comportamiento: primera solicitud reserva la clave (fila `in_progress`) en la misma transacción; al terminar guarda estado y cuerpo de respuesta; una repetición con el mismo hash devuelve la respuesta guardada; con otro hash devuelve 422 `IDEMPOTENCY_KEY_REUSED`; si está en curso devuelve 409 `IDEMPOTENCY_IN_PROGRESS`.
2. Implementar la tabla (con RLS) y la dependencia reutilizable; aplicarla a las rutas listadas (obligatoria en POS).
3. Agregar la purga de claves vencidas como tarea periódica (se ejecutará en el worker de S3.4; mientras tanto, CLI).
4. Frontend: generar una clave por operación del usuario (no por intento), conservarla hasta recibir respuesta definitiva y reenviarla en los reintentos.
5. Pruebas de repetición secuencial y concurrente.

## 9. Criterios de aceptación verificables

- Dos solicitudes simultáneas de venta rápida con la misma clave producen una sola venta, un solo descuento de stock y la misma respuesta (prueba concurrente en PostgreSQL).
- Una solicitud con la misma clave y otro cuerpo responde 422 `IDEMPOTENCY_KEY_REUSED`.
- Las rutas POS de creación sin clave responden 422 con un mensaje claro.
- El POS reintenta con la misma clave tras un timeout simulado (prueba unitaria del frontend).

## 10. Pruebas que deben ejecutarse

- Pruebas de integración concurrentes; pruebas unitarias del frontend.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core

## 11. Riesgos y posibles regresiones

- Guardar respuestas grandes (recibos) aumenta el tamaño de la tabla: limitar a 24 h y comprimir si hace falta.
- Errores 5xx no deben quedar guardados como respuesta definitiva: liberar la clave en ese caso.

## 12. Migraciones, cambios de configuración y despliegue

- Tabla nueva con RLS; desplegar core antes que web.

## 13. Estrategia de rollback o recuperación

- Desactivar la exigencia (bandera de configuración) y revertir.
