# S5.2 — Unidades de medida, presentaciones y conversiones

> **Estado:** pendiente · **Etapa 5 — Operación de ferretería** · **Tamaño:** L · **Repos:** faclab-core, faclab-web · **Brechas:** F-02, F-03

## 1. Identificador y título

`S5.2` — Unidades de medida, presentaciones y conversiones

## 2. Objetivo verificable

Cada producto tiene una unidad base de inventario y presentaciones (por ejemplo, caja de 100, rollo de 50 m) con factor de conversión, código de barras y precio propios; se compra en una presentación y se vende en otra, y el stock siempre se lleva en la unidad base.

## 3. Problema que resuelve

Las ferreterías compran por caja o rollo y venden por unidad o metro; hoy un producto tiene una sola unidad sin conversión y un solo código de barras.

## 4. Evidencia de la brecha actual

- `src/catalog/uom/domain/entities.py:7-12`: solo nombre, símbolo y activo.
- `products.barcode` único y uno por producto (`src/catalog/product/infra/models.py:33`).

## 5. Componentes y archivos que probablemente se modificarán

- `src/catalog/` (entidad `ProductPresentation` con factor, código de barras, precio; unidad base obligatoria).
- POS y ventas (línea con presentación y conversión a unidad base).
- Compras y recepciones (presentación de compra).
- Búsqueda por código de barras en el POS (`src/catalog/product/domain/specifications.py`).
- Web: catálogo, POS, compras.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- `src/catalog/`, `src/pos/`, `src/purchasing/`, docs/modules.md y los specs del módulo en `faclab-core/docs/`.

## 7. Dependencias y sesiones previas

[S5.1](S5.1-cantidades-decimales.md)

## 8. Tareas concretas en orden

1. Modelar presentaciones por producto con factor decimal respecto a la unidad base y código de barras único por empresa.
2. Hacer que la búsqueda por código de barras devuelva producto y presentación.
3. Registrar en las líneas de venta y compra la presentación, la cantidad en esa presentación y la cantidad convertida a unidad base; el stock y los movimientos usan la unidad base.
4. Mostrar al vender el precio de la presentación.
5. Adaptar el frontend (gestión de presentaciones, POS con selección de presentación, compras).

## 9. Criterios de aceptación verificables

- Comprar 2 cajas de 100 aumenta el stock en 200 unidades base; vender 15 unidades lo reduce en 15 (prueba).
- Escanear el código de barras de la caja agrega la presentación caja con su precio.
- El factor de conversión no puede ser cero ni negativo.

## 10. Pruebas que deben ejecutarse

- Pruebas de dominio, PostgreSQL y frontend.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core

## 11. Riesgos y posibles regresiones

- Ventas y facturas deben mostrar la presentación vendida; revisar el contrato con invoicing (descripción del ítem).

## 12. Migraciones, cambios de configuración y despliegue
