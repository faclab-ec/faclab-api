# S3.5 — Bitácora de auditoría de operaciones sensibles

> **Estado:** pendiente · **Etapa 3 — Integridad transaccional** · **Tamaño:** M · **Repos:** faclab-core, faclab-web · **Brechas:** G-50

## 1. Identificador y título

`S3.5` — Bitácora de auditoría de operaciones sensibles

## 2. Objetivo verificable

Las operaciones sensibles quedan en una bitácora inmutable por empresa con actor autenticado, acción, recurso, antes y después (campos relevantes), origen e id de solicitud; los administradores la consultan con filtros.

## 3. Problema que resuelve

No hay forma de saber quién cambió un precio, ajustó stock, anuló una venta, aprobó una devolución o cambió permisos.

## 4. Evidencia de la brecha actual

- No existe tabla ni módulo de auditoría (G-50); los campos de autor venían del cuerpo hasta S1.4.

## 5. Componentes y archivos que probablemente se modificarán

- Módulo `src/audit/` (entidad, repositorio, consulta, router `/api/admin/audit-log`).
- Publicación de entradas desde comandos sensibles (o desde eventos de dominio en la misma transacción).
- Permiso `audit:read`.
- faclab-web: pantalla de bitácora.
- Migración con RLS y sin `UPDATE`/`DELETE` para el rol de aplicación.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- Comandos de: cambio de precio y producto, ajustes y transferencias, anulación de ventas, devoluciones, movimientos de caja, apertura y cierre de turno, cambio de precio en el POS, usuarios y roles, membresías, sucursales, configuración fiscal.
- Bus de eventos (`src/shared/infra/events/`).

## 7. Dependencias y sesiones previas

[S2.3](S2.3-tenant-id-en-modulos.md), [S1.4](S1.4-seguridad-del-api.md)

## 8. Tareas concretas en orden

1. Definir el catálogo de acciones auditables y el formato de la entrada (sin datos sensibles).
2. Implementar el registro en la misma transacción de la operación.
3. Revocar `UPDATE` y `DELETE` sobre la tabla para el rol de aplicación.
4. Agregar la consulta paginada con filtros (fecha, actor, acción, recurso, sucursal) y la pantalla en el frontend.
5. Pruebas que verifican que cada acción del catálogo genera su entrada.

## 9. Criterios de aceptación verificables

- Cada acción del catálogo genera exactamente una entrada con actor del token (pruebas).
- El rol de aplicación no puede modificar ni borrar entradas (prueba SQL).
- La pantalla permite filtrar y ver el detalle.

## 10. Pruebas que deben ejecutarse

- Pruebas unitarias e integración; pruebas del frontend.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core

## 11. Riesgos y posibles regresiones

- Guardar valores completos puede incluir datos personales: limitar a campos relevantes.

## 12. Migraciones, cambios de configuración y despliegue

- Tabla nueva con RLS y permisos restringidos.

## 13. Estrategia de rollback o recuperación

- Revertir; la tabla queda sin uso.

## 14. Documentación que debe actualizarse

- docs/modules.md (auditoría), CLAUDE.md del core (regla: toda acción sensible nueva se audita).

## 15. Condición para declarar la sesión terminada

- Todos los criterios de aceptación se cumplen y las pruebas listadas pasan (en CI si ya existe).
- La documentación indicada está actualizada y este archivo marca *Estado: terminada* con fecha y ramas o PR.
- No quedan secretos en el código, los logs ni la documentación.
- Lo que quedó fuera de alcance está anotado como pendiente en este archivo o en ROADMAP.md.
