# S2.7 — Persistencia de faclab-invoicing en PostgreSQL

> **Estado:** pendiente · **Etapa 2 — Multiempresa y multisucursal** · **Tamaño:** L · **Repos:** faclab-invoicing, faclab-infra · **Brechas:** G-18, G-74

## 1. Identificador y título

`S2.7` — Persistencia de faclab-invoicing en PostgreSQL

## 2. Objetivo verificable

faclab-invoicing guarda facturas, configuración y certificados en una base PostgreSQL propia con migraciones versionadas, sin DynamoDB; el comportamiento externo (API HTTP, Kafka, readiness, recuperación) es idéntico; existe una restricción única de factura activa por venta y el listado de facturas está paginado.

## 3. Problema que resuelve

DynamoDB no existe en el VPS, el listado recorre toda la tabla y dos reenvíos pueden crear dos facturas activas para la misma venta.

## 4. Evidencia de la brecha actual

- Repositorios Dynamo en `src/modules/*/infra/persistence/` (unas 510 líneas detrás de interfaces de dominio).
- `dynamo-invoice.repository.ts:84-95` usa `Scan` (G-74).
- `receive-sale.ts:36-44` consulta un índice eventual y la condición del `put` solo cubre `id` (G-18).

## 5. Componentes y archivos que probablemente se modificarán

- faclab-invoicing: `src/modules/*/infra/persistence/pg-*.repository.ts` (nuevos), cliente `pg` y pool, herramienta de migraciones (elegir y justificar, por ejemplo node-pg-migrate), `migrations/`, `src/container.ts`, configuración (`DATABASE_URL`).
- faclab-invoicing: almacenamiento de certificados (cifrados en la base o en S3 compatible; decidir y documentar), ruta de listado con paginación.
- faclab-infra: base `faclab_invoicing` (script de inicialización o servicio), retirar LocalStack y dynamodb-admin si ya no se usan.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- `src/modules/*/domain/repository.ts` (contratos a respetar), mappers actuales, `src/container.ts`.
- Pruebas existentes (`test/helpers.ts` con repositorio en memoria).
- `faclab-infra/scripts/init-dynamodb.sh` (índices actuales: `SaleIdIndex`, `StatusIndex`, `SerialNumberIndex`).

## 7. Dependencias y sesiones previas

[S1.3](S1.3-empaquetado-invoicing-y-web.md), [S1.6](S1.6-contrato-de-eventos-v1.md)

## 8. Tareas concretas en orden

1. Diseñar el esquema SQL equivalente: `issuers` (todavía una fila), `certificates`, `invoices` con historial, `invoice_events`; índices por `sale_id`, `status`, fecha.
2. Agregar la restricción única parcial de factura activa por venta y traducir su violación a la deduplicación existente.
3. Implementar los repositorios PostgreSQL respetando las interfaces; optimistic locking con columna `version`.
4. Reemplazar el contador `ADD invoice_sequence` por una fila de secuencia con `UPDATE ... RETURNING` (todavía global, se vuelve por punto de emisión en S2.8) y corregir el arranque en 000000002.
5. Paginar `GET /api/invoices` (limit/offset y filtros por estado y fecha) manteniendo la respuesta compatible con faclab-web o actualizándola en la misma entrega.
6. Escribir pruebas de repositorio contra PostgreSQL (contenedor en CI).
7. Actualizar faclab-infra para crear la base de facturación y documentar el arranque local.

## 9. Criterios de aceptación verificables

- No queda ninguna importación de `@aws-sdk/client-dynamodb` en `src`.
- El flujo venta → factura autorizada (SRI de pruebas o simulado) funciona igual que antes (prueba manual documentada y pruebas automatizadas).
- Dos `sales.confirmed` de la misma venta con distinto `event_id` procesados en paralelo dejan una sola factura activa (prueba).
- La primera factura de un emisor nuevo tiene secuencial 000000001.
- `GET /api/invoices` devuelve páginas con total.

## 10. Pruebas que deben ejecutarse

- Pruebas de repositorio con PostgreSQL y las existentes de flujo, readiness y recuperación.
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`
- faclab-infra: `docker compose config -q` y levantar los servicios afectados

## 11. Riesgos y posibles regresiones

- Cambiar la persistencia puede alterar la semántica de concurrencia (versionado optimista): cubrir con pruebas.
- faclab-web consume la lista de facturas: coordinar el cambio de forma de la respuesta.

## 12. Migraciones, cambios de configuración y despliegue

- Base nueva `faclab_invoicing`; sin migración de datos desde DynamoDB (solo hay datos de desarrollo).
- Variables nuevas: `DATABASE_URL`; retirar las de DynamoDB.

## 13. Estrategia de rollback o recuperación

- Mantener la rama anterior desplegable; los datos de desarrollo se recrean.

## 14. Documentación que debe actualizarse

- README de faclab-invoicing y faclab-infra.
- ADR-0004 (aceptado) y docs/architecture/CURRENT_STATE.md §4.
