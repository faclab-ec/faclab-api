# S2.7 — Persistencia de faclab-invoicing en PostgreSQL

> **Estado:** terminada (2026-10-20) · rama `feat/s2-7-invoicing-en-postgresql` en faclab-infra (`3ea2d60`), faclab-invoicing (`67cb9d7`), faclab-web (`7cd69a4`) y faclab-core (el de documentación) · PR faclab-infra#4, faclab-invoicing#47, faclab-web#109, faclab-api#124 · **Etapa 2 — Multiempresa y multisucursal** · **Tamaño:** L · **Repos:** faclab-invoicing, faclab-infra (y faclab-web) · **Brechas:** G-18, G-74

## 1. Identificador y título

`S2.7` — Persistencia de faclab-invoicing en PostgreSQL

## 2. Objetivo verificable

faclab-invoicing guarda facturas, configuración y certificados en una base PostgreSQL propia con migraciones versionadas, sin DynamoDB; el comportamiento externo (API HTTP, Kafka, readiness, recuperación) es idéntico; existe una restricción única de factura activa por venta y el listado de facturas está paginado.

## 3. Problema que resuelve

DynamoDB no existe en el VPS, el listado recorre toda la tabla y dos reenvíos pueden crear dos facturas activas para la misma venta.

## 4. Evidencia de la brecha actual

- Repositorios Dynamo en `src/modules/*/infra/persistence/` (unas 510 líneas detrás de interfaces de dominio).
- `dynamo-invoice.repository.ts:84-95` usa `Scan` (G-74).
- `receive-sale.ts:36-44` consulta un índice eventual y la condición del `put` solo cubre `id` (G-18).

## 5. Componentes y archivos que probablemente se modificarán

- faclab-invoicing: `src/modules/*/infra/persistence/pg-*.repository.ts` (nuevos), cliente `pg` y pool, herramienta de migraciones (elegir y justificar, por ejemplo node-pg-migrate), `migrations/`, `src/container.ts`, configuración (`DATABASE_URL`).
- faclab-invoicing: almacenamiento de certificados (cifrados en la base o en S3 compatible; decidir y documentar), ruta de listado con paginación.
- faclab-infra: base `faclab_invoicing` (script de inicialización o servicio), retirar LocalStack y dynamodb-admin si ya no se usan.

### Brechas confirmadas antes de cambiar el código

- **G-74**: `findAll()` hacía `Scan` con paginación interna de DynamoDB (`dynamo-invoice.repository.ts:84-95`).
- **G-18**: `ReceiveSaleCommand` consultaba `SaleIdIndex` (lectura eventual) y el `put` solo condicionaba
  el `id` (`receive-sale.ts:36-44`).
- **G-09**:
  - El arranque en `000000002` se confirmó: `CompanyConfig.create` guardaba `invoice_sequence = 1` y
    `ADD 1` devolvía 2.
  - La reescritura del contador al guardar la configuración también (`company-config.commands.ts:40-46`).

### Decisiones

- **Tuyas**:
  - El `.p12` se guarda cifrado en PostgreSQL, no en S3.
  - La base local de facturación es un servicio propio de faclab-infra.
  - faclab-web se actualiza en la misma entrega para paginar en el servidor.
- **Técnicas** (justificadas en ADR-0004, ahora aceptado):
  - `pg` con SQL a mano, sin ORM.
  - node-pg-migrate con migraciones `.sql`: up y down, advisory lock y tabla `pgmigrations`. La v9 es
    solo ESM, así que el servicio usa su CLI y solo las pruebas importan su API (`test/tsconfig.json`
    con `moduleResolution: bundler`).
  - `@opentelemetry/instrumentation-pg` reemplaza a `instrumentation-aws-sdk`, con
    `requireParentSpan`, para no perder los spans de base de datos.
  - Se retiraron `@aws-sdk/client-dynamodb`, `lib-dynamodb`, `util-dynamodb`, `client-s3`,
    `@aws-sdk/types` e `instrumentation-aws-sdk`.
- **Esquema**:
  - `invoices`, con `version` y `uq_invoices_active_sale (sale_id) WHERE status <> 'rejected'`;
  - `invoice_events`, el historial, que solo crece;
  - `issuers`, una fila;
  - `sequences (doc_type, last_value)`, global;
  - `certificates`, con `p12_ciphertext` y `password_ciphertext`.
- **Factura activa única**: `createInvoice` usa `INSERT ... ON CONFLICT DO NOTHING`. Si el id ya existe
  o la venta ya tiene una factura activa, devuelve `false` y el reenvío sigue el camino de deduplicación
  de siempre (log "already received or with an active invoice").
- **Secuencial**:
  - `nextInvoiceSequence()` es `UPDATE sequences ... RETURNING`.
  - `invoiceSequence` de la configuración pasa a significar "el número que tomará la próxima factura";
    con eso un emisor nuevo empieza en 1.
  - Guardar la configuración sin el campo no toca el contador; con el campo, lo fija
    (`setNextInvoiceSequence`).
  - `invoiceSequence` ahora debe ser entero.
- **`GET /api/invoices`**:
  - Parámetros: `limit` (1-1000, 100 por defecto, como `QueryParams` del core), `offset`, `status`,
    `fromDate`/`toDate` (días en America/Guayaquil, ambos incluidos) y `attention`.
  - Responde `data: [...]` con `meta.pagination: { total, limit, offset }`, igual que
    `PaginatedDataResponse` del core.
- **Certificados**:
  - Se borraron `FileStoragePort` y `S3StorageAdapter`.
  - El archivo y la contraseña se guardan en una sola escritura, así una subida que falla ya no deja
    un archivo suelto.
  - La respuesta pierde `s3Url`, que faclab-web no mostraba.
- **Ids que no son uuid**: los repositorios los tratan como inexistentes. Así se mantiene el "Invoice
  not found" de antes para un mensaje de Kafka con un id mal formado.
- **Puerto local 5434**: en esta máquina el 5433 lo ocupa otro proyecto; se cambia con
  `INVOICING_DB_PORT`.

### Prueba manual

Hecha con faclab-infra (Kafka e `invoicing-db`) y `npm run dev`:

1. `npm run migrate up` (también `down` y `up` otra vez).
2. El consumidor tomó un `sales.confirmed` que había quedado en Kafka y lo guardó `pending` con
   `CONFIG_MISSING`.
3. Se publicaron con `kafka-console-producer` dos `sales.confirmed` de la venta 9001, a partir del
   ejemplo `full-customer.json` del contrato, con distinto `event_id`. Quedó una sola factura.
4. `GET /api/invoices` devuelve `meta.pagination`; `?attention=true&limit=10` devuelve las dos facturas
   pendientes.
5. `PUT /api/company-config` sin certificado responde con `invoiceSequence: 1`, y el estado pasa a
   `CERTIFICATE_NOT_SELECTED`. El reintento manual registra esa incidencia; un `invoiceSequence` no
   entero responde 400.
6. Se subió un `.p12` autofirmado generado para la prueba: quedó cifrado en la base (`v1:`, sin la
   contraseña en claro), el listado no trae `s3Url` y se pudo borrar.
7. El build compilado se apaga limpio con SIGTERM (pool cerrado, salida 0).

**Lo que no se hizo en la prueba manual:**

- Llegar a `authorized` contra el SRI de pruebas, porque necesita un certificado válido: lo cubre la
  prueba automatizada con el SRI simulado.
- Originar la venta desde el POS del core: el core no cambia en esta sesión y el mensaje sigue el
  contrato v1. Para repetirlo de punta a punta: `make dev` en el core con Kafka, una venta del POS,
  `GET /api/invoices/by-sale/<id>`.

### Despliegue

- Migración y entorno local:
  - Base nueva, sin migración de datos desde DynamoDB: los datos de desarrollo se recrean
    (configuración y certificados se cargan de nuevo).
  - En faclab-infra: `docker compose up -d --remove-orphans`. Después se pueden borrar
    `.docker/.volumes/aws` y las variables `LOCALSTACK_*` del `.env`.
  - En invoicing: agregar `DATABASE_URL` al `.env` (lo lee `npm run migrate`) y correr
    `npm run migrate up` antes de `npm run dev`.
- Orden: faclab-infra → faclab-invoicing (migrar y luego arrancar) → faclab-web. Una web anterior con
  el invoicing nuevo ve solo las 100 facturas más recientes.
