# S4.3 — Conciliación entre ventas y comprobantes, y reproceso de fallidos

> **Estado:** pendiente · **Etapa 4 — Facturación robusta** · **Tamaño:** M · **Repos:** faclab-core, faclab-invoicing, faclab-web · **Brechas:** G-21

## 1. Identificador y título

`S4.3` — Conciliación entre ventas y comprobantes, y reproceso de fallidos

## 2. Objetivo verificable

Una tarea periódica detecta ventas confirmadas sin resultado de facturación después de X minutos, comprobantes autorizados de ventas anuladas y diferencias de totales; los operadores ven las discrepancias y pueden reenviar o reprocesar desde la interfaz; existe una herramienta para reprocesar la DLQ de invoicing.

## 3. Problema que resuelve

Si un mensaje se pierde o queda fallido, nadie se entera hasta que el cliente reclama su factura.

## 4. Evidencia de la brecha actual

- No hay conciliación entre servicios; el reenvío manual existe (`POST /api/admin/sales/{id}/request-invoice`) pero no hay forma de saber qué reenviar.
- La DLQ de invoicing no tiene herramienta de reproceso.

## 5. Componentes y archivos que probablemente se modificarán

- faclab-core: tarea en el worker, tabla o vista de discrepancias, endpoint de listado, métricas (S7.1 las expone).
- faclab-invoicing: endpoint de consulta por lote de ventas (o publicación de un resumen) y CLI o endpoint de reproceso de la DLQ.
- faclab-web: vista de "requiere atención" en ventas.

## 6. Archivos o módulos que deben inspeccionarse antes de editar

- Reenvío existente (`SaleInvoicingRequested`), estado `invoice_status` (S3.4), vista de facturas con atención en faclab-web.

## 7. Dependencias y sesiones previas

[S3.4](S3.4-worker-y-mensajeria-resiliente.md), [S4.2](S4.2-sri-desacoplado.md)

## 8. Tareas concretas en orden

1. Definir los tipos de discrepancia y sus umbrales.
2. Implementar la tarea de conciliación en el worker del core con consulta a invoicing por lotes (HTTP interno autenticado con token de servicio) o por estado ya recibido en `invoice_status`.
3. Exponer el listado y las acciones (reenviar, marcar revisado) con auditoría.
4. Implementar el reproceso de la DLQ de invoicing (por id o por lote) con auditoría.
5. Agregar la vista en el frontend.

## 9. Criterios de aceptación verificables

- Una venta cuyo mensaje se borra del outbox aparece como discrepancia y se resuelve con el reenvío (prueba).
- Un mensaje en la DLQ de invoicing se reprocesa y genera su factura.
- La vista muestra solo discrepancias de la empresa del usuario.

## 10. Pruebas que deben ejecutarse

- Pruebas de integración en ambos servicios; pruebas del frontend.
- faclab-core: `make lint && make typecheck && .venv/bin/python -m pytest tests/ -q`
- faclab-core: `make test-integration` si cambian modelos, migraciones, consultas SQL o flujos con PostgreSQL
- faclab-invoicing: `npm run lint && npm run typecheck && npm test`
- faclab-web: `npx tsc --noEmit && npm run lint && npm test`
- faclab-web: `npm run test:e2e` si cambian flujos de interfaz; `OPENAPI_URL=http://localhost:3000/openapi.json npm run check:contract` si cambia el contrato con el core

## 11. Riesgos y posibles regresiones

- Consultas masivas entre servicios: paginar y limitar la frecuencia.

## 12. Migraciones, cambios de configuración y despliegue

- Tabla de discrepancias (opcional) y token de servicio entre core e invoicing.

## 13. Estrategia de rollback o recuperación

- Desactivar la tarea por configuración.
